# Why the MVP demos laptop-scale models

The FrugalMind demo leaderboard is deliberately populated with **small, open,
locally-runnable models** (7–8B, via Ollama) rather than frontier APIs. That is
a design decision, not a limitation of the harness — which runs frontier models
just as happily. Here is the reasoning.

## 1. It is the thesis under test

FrugalMind's claim is that **the interesting winner is not the highest score —
it is the cheapest system that still clears the quality floor.** You cannot
demonstrate that claim with a leaderboard of frontier models, because every row
would clear the floor and the cost axis would be decoration.

The claim only becomes falsifiable when the board contains models that *don't*
automatically clear the floor. A 7B model that fails a task ungrounded, and then
clears it once a domain skill is loaded, **is the result** — it is the evidence
that a cheap model plus good scaffolding substitutes for an expensive one. That
is the whole frugality argument, and it is only visible at small scale.

## 2. Reproducibility without a credit card

Every number on the demo board can be regenerated by a reader with a laptop and
no API keys, no cloud account, and no budget approval:

```bash
ollama pull qwen2.5:7b llama3.1:8b deepseek-r1:7b olmo2:7b
pixi run -e full python scripts/demo_dashboard.py
```

A benchmark whose results only a funded lab can reproduce is a benchmark that
gets taken on faith. That is precisely the "evidence, not hype" failure mode
FrugalMind exists to fight. Local models make the leaderboard *auditable*.

## 3. Scientific data often cannot leave the building

Much geoscience work runs on embargoed catalogs, unpublished waveforms,
pre-publication figures, and collaborator data under agreement. Sending that to
a third-party API is frequently not allowed and always a judgement call. A
benchmark that only measures API models cannot tell a lab anything about the
tools they are actually permitted to use on their real data.

Local, open-weight models are the ones that can legally touch the data. So they
are the ones worth measuring.

## 4. Equity of access

The labs with the least budget are the ones that most need to know whether a
cheap model suffices. A leaderboard dominated by frontier models tells a
well-funded group what it already suspects and tells everyone else nothing
actionable. Measuring at laptop scale produces advice that is usable by a
graduate student on a department machine.

## 5. Transparency and contamination

Open-weight models — and especially **fully open** ones like AI2's OLMo, where
the training *data* and code are published — let you reason about whether a
benchmark item leaked into training. With a closed API model you are guessing.
For a benchmark that takes hidden splits and `cutoff_date` seriously (see
[`dataset_submission.md`](dataset_submission.md)), that traceability is
part of the scientific instrument, not a nice-to-have.

## 6. MVP scope: validate the harness before spending

Before spending real money on frontier evaluation, we want confidence that the
substrate is sound: the scorers are deterministic, the sandbox is reproducible,
the skill-injection modes are wired, the telemetry and cost accounting are
correct, and the leaderboard renders what actually happened. Small local models
exercise every one of those paths at zero marginal cost, and they fail *more*
often — which is exactly what you want when you are trying to find bugs in a
scorer.

Frontier models are a later, cheap addition: the registry already carries them
(`config/models.yaml`, `cloud` tier), and adding a row is one CLI flag.

## What the current demo actually is (and is not)

**Be precise about this.** The demo board on the landing page is a *harness
demonstration*:

- The **scorers, suites, truth sets, sandbox, and cost model are real** — they
  are the same code paths a live run uses.
- The **model responses are simulated deterministically** (a per-model
  competence profile decides whether the model emits a sound or unsound answer),
  because CI has no GPU, no Ollama daemon, and no API keys.

So the board proves *the platform works end to end and the scoring
discriminates*; it does **not** yet publish real measured capability for these
models. Replacing the simulation with live Ollama calls is a one-line adapter
swap (see `scripts/demo_dashboard.py` and the notebooks), and those numbers —
once produced on a machine with the models pulled — are the ones that belong on
a published leaderboard.

We label this clearly on the dashboard rather than letting a synthetic number be
mistaken for a measurement. That labelling *is* the point of the project.
